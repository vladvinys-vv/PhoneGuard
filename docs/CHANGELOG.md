# Changelog

## [Unreleased] — интеграции и исправления

### Fixed
- **Фоновое выживание: сирена обрывалась, команда «остановить» из фона терялась**
  (+13 проверок, 836 → 849 тестов (86 → 87 файлов)):
  - **Сирена жила в фоновом процессе.** `MediaPlayer` в `SecurityService` — обычный фоновый
    процесс, первый кандидат на убийство при нехватке памяти: тревога обрывалась на середине,
    и телефон замолкал. Именно тогда, когда она нужнее всего: сигнал включают из SMS-команды
    или после загрузки, то есть приложение давно в фоне. Добавлен
    `antitheft/AlarmHoldService` (foreground, `specialUse`): звуком он не управляет — держит
    процесс и `START_STICKY`-перезапуском восстанавливает тревогу по сохранённому режиму
    потери, если процесс всё-таки убили.
  - **«Остановить» из фона не срабатывало.** `ShoulderSurferService.stop()` и
    `FirewallViewModel.stopVpn()` вызывали `startService()`, который вне foreground бросает
    `IllegalStateException`: интерфейс показывал «выключено», а детектор подглядывания или
    VPN-туннель продолжали работать. Остановка переведена на `stopService()` (разрешён из
    любого состояния), очистку делает `onDestroy`.
  - **Правила фонового запуска собраны в одном месте.** Новый чистый
    `util/BackgroundStartPolicy` отвечает, можно ли поднять foreground-сервис из данного
    триггера (`USER_VISIBLE`, `BOOT_COMPLETED`, `DEVICE_ADMIN`, `SMS_COMMAND`, `WORKER`,
    `UNKNOWN`), и что делать при отказе: сообщить пользователю, показать уведомление вместо
    SMS-ответа или отложить. Device admin — исключение из ограничений Android 12+, поэтому
    анти-кража по SMS-команде продолжает звучать.
- **Уведомления: «залипшие» предупреждения и каналы, которые никогда не обновлялись**
  (+14 проверок, 822 → 836 тестов (85 → 86 файлов)):
  - **Остановленная тревога оставляла уведомление о вторжении.** `stopAlarm()` гасил сирену, но
    не отменял уведомление 8102: предупреждение висело, пока пользователь не тронет его пальцем,
    и выглядело как продолжающееся событие. То же при естественном окончании сирены
    (`soundSirenFor`). Теперь оба пути гасят уведомление по таблице `NotificationChannels`.
  - **Предупреждение «кто-то смотрит в экран» не исчезало никогда.** Ни `stopDetection()`, ни
    `onDestroy()` не отменяли 1003 — после выключения детектора уведомление оставалось.
  - **Имя и описание каналов не доезжали до пользователя.** Три `ensureChannel()` начинались с
    `if (getNotificationChannel(id) != null) return`, поэтому канал создавался один раз в первой
    версии и жил с тем текстом: правки формулировок и переводы не применялись. Теперь канал
    создаётся/обновляется при каждом показе (Android обновляет имя и описание существующего
    канала).
  - **Девять мест знали про каналы по-своему.** id и важность канала были `private const` в
    каждом сервисе; теперь это одна таблица `util/NotificationChannels.Spec`, а установка —
    `util/NotificationChannelInstaller`. Важность существующего канала менять нельзя, поэтому
    если канал на устройстве тише требуемого (старая версия или пользователь приглушил), это
    пишется в журнал: иначе предупреждения просто не слышны, и никто об этом не знает.
  - **Предупреждение о подглядывании на Android 13+.** `notify()` вызывался без проверки
    `POST_NOTIFICATIONS` и без перехвата `SecurityException` прямо из ML Kit-колбэка — теперь
    проверка разрешения и `runCatching`, как в остальных уведомлениях.
  - Документация по id приведена в порядок: в таблице `docs/DEVELOPMENT.md` 8101 числился за
    `SmsCommandReceiver`, хотя тот использует 8103; добавлены 8102, 8103 и диапазон 20 000+.
- **Релизный контур: молча неподписанная сборка, дубль versionCode, правила R8 без проверки**
  (+10 проверок, 812 → 822 теста (84 → 85 файлов)):
  - **`assembleProductionRelease` без keystore собирал неподписанный APK.** Сборка зелёная,
    артефакт для публикации негоден — и это видно только тому, кто откроет файл. Теперь
    `app/build.gradle` проверяет граф задач и падает с понятным сообщением; проверочная сборка
    без подписи возможна только явно (`-PallowUnsignedRelease=true`), `build_release.sh` включает
    флаг сам и печатает предупреждение. Пустой `storeFile=` больше не считается keystore:
    `file("")` — это каталог проекта, он «существует», и подпись уходила с пустыми паролями.
  - **`versionCode` был зашит единицей.** Второй релиз из тега получал тот же `versionCode`,
    который Play уже не принимает. Теперь версия задаётся `-PpgVersionCode`/`-PpgVersionName`
    (или `PG_VERSION_CODE`/`PG_VERSION_NAME`), а Codemagic считает её из тега `v1.2.3`
    (`10203`) или из номера сборки; тег другого формата — ошибка сборки.
  - **Отчёт сканирования зависел от R8.** `Gson().toJson(report)` пишет имена Kotlin-полей,
    которые R8 переименовывает: в релизе в `report_json` уезжали ключи вида `{"a":50}`, и
    спасал только широкий `-keep` на весь пакет `model`. Заменён на `ScanReportJson` —
    ключи-литералы, фиксированный порядок, общее с выгрузкой экранирование; зависимость
    `gson` и её правило удалены.
  - **Правила R8 не проверялись вообще.** Новый `tools/proguard_check.py` сверяет их с кодом и
    зависимостями: правило для несуществующего пакета (`com.phoneguard.privacyscanner.**` — такого
    пакета нет), правило для удалённой библиотеки, строковый `Class.forName("com.phoneguard.…")`
    без `-keep`, отсутствие `Signature` при рефлексивной сериализации. Отдельно считается доля
    собственных классов под `-keep` (162 из 215, 75 %) — предупреждение о том, что сжатие
    почти не работает; снижать её можно только по результатам настоящей релизной сборки.
  - **Codemagic.** Добавлены шаги «R8 rules check» и «Materialise release keystore» (keystore из
    `KEYSTORE_BASE64`), сборка `bundleProductionRelease` (в артефактах значился `.aab`, но никто
    его не собирал), `mapping.txt` в артефактах и требование подписи для тегов `v*`.
- **Отзыв разрешений на ходу: защита молча деградировала** (+11 проверок, 801 → 812 тестов
  (83 → 84 файла)):
  - **Никто не проверял, что разрешения ещё на месте.** Они запрашивались один раз на
    онбординге, а дальше `checkSelfPermission` встречался в одиннадцати файлах с разной
    реакцией: где-то `return` без записи в журнал, где-то `Log.w`, где-то уведомление. Пользователь
    мог отозвать `CAMERA`, `SEND_SMS`, `READ_PHONE_STATE` или `POST_NOTIFICATIONS` — и функции
    тихо переставали работать, без единого признака в интерфейсе.
  - **Детектор подмены SIM отключался молча.** `SimSwapDetector.checkSimState()` при отсутствии
    `READ_PHONE_STATE` просто выходил — теперь пишет предупреждение в журнал, а пользователь
    видит ослабленную защиту на дашборде.
  - **Таблица «возможность → разрешение».** Новый чистый `ProtectionCapabilityPolicy` знает,
    что без `READ_PHONE_STATE` не работает детектор подмены SIM, без `CAMERA` — съёмка
    нарушителя, без `SEND_SMS` — SMS доверенным контактам, без `ACCESS_FINE_LOCATION` —
    координаты при подмене SIM, а без `POST_NOTIFICATIONS` — предупреждения о вторжении.
    `POST_NOTIFICATIONS` требуется только с Android 13: до него такого разрешения нет, и
    предупреждать о нём было бы ложной тревогой.
  - **Сводка на дашборде.** Карточка «Защита работает не полностью» перечисляет ослабленные
    функции, используя уже существующие объяснения разрешений; список пересчитывается при
    возврате на дашборд, потому что разрешение могли отозвать в системных настройках, пока
    приложение было в фоне. Новых экранов нет.
- **VPN: двойное закрытие дескриптора и «висящий» сервис после перезапуска** (+11 проверок,
  790 → 801 тест (82 → 83 файла)):
  - **Дескриптор туннеля закрывали двое.** Цикл чтения закрывал
    `FileInputStream(iface.fileDescriptor)`, а `stopVpn()`/`restartTunnel()` независимо вызывали
    `vpnInterface?.close()` на том же дескрипторе. Второе закрытие идёт по номеру, который к
    этому моменту мог быть выдан другому сокету. Теперь владелец один —
    `ParcelFileDescriptor.AutoCloseInputStream`: закрывается только поток (он же разблокирует
    висящий `read`), отдельного `iface.close()` нет; единственное исключение — если поток
    создать не удалось.
  - **Перезапуск системой оставлял сервис без уведомления.** `START_STICKY` перезапускает сервис
    с пустым интентом, а ветка `else` не поднимала туннель и не завершала сервис — он висел,
    хотя `startForegroundService` требует `startForeground()` в первые пять секунд. Разбор
    команды вынесен в чистый `VpnLifecyclePolicy`: `CONNECT` — поднять (или оставить живой),
    `DISCONNECT` — остановить, пустой интент без туннеля — завершиться, пустой интент при живом
    туннеле — оставить и восстановить уведомление.
  - **Два цикла чтения одновременно при смене сети.** `restartTunnel()` отменял задачу
    асинхронно и сразу закрывал интерфейс, поэтому старый цикл мог выполнить свой `finally` уже
    после создания нового туннеля. Теперь закрытие дескриптора идёт до `startVpn()`, а цикл
    сверяет владельца по ссылке на поток.
  - `onDestroy()` больше не зовёт `stopVpn()` (тот делал `stopForeground`/`stopSelf` из уже
    умирающего сервиса), а освобождает ресурсы напрямую.
- **Threat Intelligence: фид качался параллельно, кэш жил по стеновым часам** (+9 проверок,
  781 → 790 тестов (81 → 82 файла)):
  - **Дублирующиеся загрузки.** Признак «фид свежий» проверялся вне блокировки, а время
    загрузки записывалось только после неё: несколько одновременных проверок хостов каждая
    тянула фид OpenPhish заново — до 8 МБ на мобильном трафике за раз. Добавлен `Mutex`
    (single-flight) с перепроверкой условия под блокировкой: пока поток ждал, фид мог
    загрузить кто-то другой.
  - **Время по стеновым часам.** `System.currentTimeMillis()` в TTL кэша означало, что перевод
    часов назад держит запись (в том числе вердикт «неизвестно») бесконечно, а вперёд —
    сбрасывает весь кэш без причины. Кэш и расписание фида переведены на монотонное
    `SystemClock.elapsedRealtime()`.
  - **Пустой ответ и ошибка сети теперь разные.** Раньше пустой фид кодировался арифметикой
    `now - TTL + RETRY`, а исключение запроса вообще не обрабатывалось. Новый чистый
    `ThreatFeedRefreshPolicy`: успех — 6 часов, пустой ответ — час, ошибка сети — 10 минут, и
    явное «когда можно повторить» вместо вычисления на месте.
  - Старый фид при сетевой ошибке остаётся в работе (fail-open сохраняется): кэш не затирается.
- **Настройки против поведения: мёртвая настройка и сканирование вопреки выбору**
  (+7 проверок, 774 → 781 тест (80 → 81 файл)):
  - **`ScheduledFullScanWorker` не проверял настройку.** Работа, поставленная до выключения,
    восстановленная планировщиком или оставшаяся от прошлой версии, выполняла полное
    сканирование устройства уже после того, как пользователь выключил периодичность. Теперь
    воркер проверяет настройку на каждом запуске и тихо завершается
    (`ScanSchedulePolicy.verdict`), а не повторяет запуск.
  - **Неудача планировщика оставляла настройку включённой.** Флаг сохранялся до постановки
    работы, поэтому при отказе планировщика интерфейс показывал «включено», а сканирование не
    приходило никогда. Теперь неудача возвращает настройку назад
    (`ScanSchedulePolicy.shouldRevert`) и пишется в журнал.
  - **Удалена мёртвая настройка «защита чувствительных приложений».** Ключ
    `sensitive_apps_guard_enabled` (по умолчанию `true`) читался единственным потребителем —
    `SimSwapDetector.enableSensitiveAppsGuard()`, тело которого было комментарием
    «Guard will be handled via accessibility observer in existing app lock flows». Парная
    `disableSensitiveAppsGuard()` тоже ничего не делала, а в интерфейсе настройки нет вовсе.
    Обещать защиту, которой нет, хуже, чем не обещать: настройка, сеттер и заглушки удалены.
- **Контур вторжения: дребезг реакций, обрыв плана, молчаливые отказы** (+13 проверок,
  761 → 774 теста (79 → 80 файлов)):
  - **Серия событий давала серию активных реакций.** Пять одинаковых событий — пять правил
    фаервола на один пакет, пять SMS доверенным контактам, пять запусков скрытой съёмки. У
    приманок антидребезг был (`HoneypotReportGate`), у остальных действий — нет. Добавлен
    `intrusion/IntrusionReactionGate`: активное действие не чаще раза в 30 с на пару
    «тип события + пакет + действие»; предупреждение, выгрузка в журнал, запирание сейфа и
    приманки не подавляются никогда (иначе серия событий исчезла бы из журнала — ровно та
    ошибка, которую исправлял `IntrusionResponsePolicy`).
  - **Одно упавшее действие отменяло весь остаток плана:** исключение в `blockPackage`
    оставляло пользователя без предупреждения и без фото. Теперь каждое действие в своём
    `try/catch` с записью в журнал.
  - **Настройки реакции читались по одной на каждое действие** (до шести обращений к DataStore
    на событие, каждое в своей точке приостановки). Снимок настроек снимается один раз на
    событие — при серии событий план больше не выполняется по «плавающим» значениям.
  - **Молчаливые отказы:** без разрешения CAMERA снимок не делался, без SEND_SMS уведомление
    не уходило, при пустом списке контактов SMS просто не отправлялось, а исключение запуска
    foreground-сервиса камеры съедалось `catch (_: Exception) {}`. Снаружи «сработало» и «не
    сработало» выглядели одинаково. Все четыре случая пишут причину в журнал.
- **Перезагрузка выключала анти-кражу, а неподтверждённая подмена — детектор SIM**
  (+5 проверок, 756 → 761 тест):
  - Сирена режима потери жила только в памяти. Достаточно было перезагрузить телефон, чтобы
    звук пропал навсегда, а приложение продолжало показывать «режим потери включён».
    Добавлен `antitheft/BootAlarmReceiver` (`BOOT_COMPLETED` + `MY_PACKAGE_REPLACED`) и
    `SecurityService.resumeAfterBoot()`; правило — чистое `LostModePolicy.onDeviceBoot`
    (разница с `onRestore`: «приложение запустили» — тихо, «телефон загрузили» — сирена снова).
    `alarmPlaying` выставляется только по факту созданного плеера: «врать про тревогу» нельзя.
  - `SimSwapReceiver` проверял SIM только `if (!detector.hasUnconfirmed())`. Флаг в DataStore
    работал как выключатель детектора: пока пользователь не ответил на уведомление (или процесс
    убили до ответа), новые события SIM не проверялись вообще, и вторая подмена не замечалась.
    Проверка выполняется всегда — повторов это не даёт, потому что после подмены эталон уже
    обновлён и то же состояние даёт `IGNORE`. Неиспользуемый `hasUnconfirmed()` удалён.
  - Оба приёмника создавали `CoroutineScope` на каждый экземпляр (приёмник пересоздаётся на
    каждый broadcast) — джобы никто не отменял. Области перенесены на уровень процесса.
- **Фишинг в SMS: обфускация, свежие зоны, омоглифы** (+11 проверок, 745 → 756 тестов):
  - **Обфускация ссылок не распознавалась вовсе.** `sberbank-online[.]ru`, `paypal(.)com`,
    `bank{dot}de`, `hxxp://…`, `sberbank . ru` — так пишут половину фишинговых SMS именно для
    обхода фильтров. Метка `[` не проходила проверку символов, токен отбрасывался — «ссылки нет»,
    сообщение чистое. Добавлено снятие маскировки (`[.]`, `(.)`, `{.}`, `[dot]`, `(dot)`, `{dot}`,
    `hxxp(s)://`, точка в пробелах) перед поиском ссылок.
  - **Голый домен в новой зоне не считался ссылкой.** Зоны были перечислены руками (`.ru`, `.com`,
    `.xyz`, …), поэтому `sberbank-online.icu`, `evil.app`, `яндекс.рф` проходили как «сообщение без
    ссылки». Правило заменено на форму: 2–24 буквы любого алфавита, кроме известных расширений
    файлов (`photo.jpg`, `index.html` — не сайты).
  - **Омоглиф-подмена не замечалась.** `аpple.com` с кириллической «а» выглядел обычным доменом.
    Теперь имя хоста со смешанными алфавитами в одной метке — самостоятельный признак атаки, без
    «давящих» слов; целиком кириллический `яндекс.рф` под правило не попадает.
  - **Ключевые слова искались подстрокой:** `код` находился в «кодексе», `карта` в «картоне»,
    `verify` в «verifying». Сравнение переведено на слова через `NamePatternMatcher`: короткие
    слова — только целиком, длинные — по основе (`подтвер` → «подтвердите/подтверждено»).
- **Тревога по SMS могла не звучать и утекала ресурсами** (+4 проверки, 741 → 745 тестов):
  - `SmsCommandReceiver` играл `Ringtone` от `TYPE_ALARM` — а рингтон играет на канале
    **звонка**, поэтому в беззвучном режиме и под «Не беспокоить» удалённая тревога молчала
    ровно тогда, когда она нужна. Команда `ALARM` переведена на общий плеер
    (`SecurityService.soundSirenFor`, `USAGE_ALARM`) — он звучит в любом режиме и поднимает
    громкость канала будильника.
  - Там же на каждую команду создавались `Ringtone` и `Handler` c отложенным `stop()`;
    повторная команда давала **две независимые сирены** одновременно, а отменить их было
    нечем. Теперь сирена одна, повторный вызов переиспользует плеер.
  - `LostModePolicy.onSirenSilenced` — затухание сирены гасит только звук: режим потери

  нет разрешений → запрос не выполняется), 3 выполняемых теста.
- **Остановка детектора подглядывания блокировала главный поток.** `ShoulderSurferService.stopDetection`
  вызывал `ProcessCameraProvider.getInstance(this).get()` прямо в main-потоке: если провайдер камеры
  ещё инициализировался (а выключить слежку можно сразу после включения), поток стоял вплоть до ANR.
  Развязка камеры теперь асинхронная, через `addListener` (как уже было в `StealthCameraService`).
- **Политика блокировки звонков вынесена в `CallBlockDecision`.** Порядок «белый список → чёрный
  список → спам-база → скрытый номер → неразобранный номер → международный» был выписан прямо в
  сервисе с `Context`/Room/DataStore и не проверялся ни одним тестом; ошибка в порядке означала бы
  потерю звонков, которые пользователь сам разрешил. 9 выполняемых тестов, включая приоритет белого
  списка над всеми остальными правилами. Чтения БД и настроек остались с короткими замыканиями.
- **Признаки служб доступности вынесены в `AccessibilityHeuristics`.** Совпадение шаблонов
  (`autoclick`, `keylog`, `screenshot`, …) по имени пакета и ярлыку теперь сравнивается в
  `Locale.ROOT` и покрыто 7 тестами, включая переключение локали на турецкую.
- **Выгрузка журналов держала в памяти три копии всех логов, а enum'ы писались непредсказуемо.**
  `LogExporter` собирал `JSONArray` + `JSONObject`, затем ещё и строку `json.toString(2)` — при
  выгрузке за 90 дней это несколько копий сразу (риск OOM на слабом устройстве), а
  `JSONObject.put(name, enum)` не документирует сериализацию `connectionType`/`trafficDirection`:
  объект enum'а мог уехать в файл без кавычек (невалидный JSON) либо уронить `toString()`, и
  выгрузка молча возвращала `null`. Теперь JSON пишется сразу в буфер файла через `ExportJson`
  (9 выполняемых тестов: экранирование кавычек/переводов строк/управляющих символов, `null` для
  необязательных полей, `WIFI`/`OUTBOUND` строками, сохранение UTF-8 без `\u`-эскейпов).
  Недописанный файл при ошибке удаляется — раньше он оставался и выглядел как успешная выгрузка.
- **Установка приложения могла стереть предупреждение о подмене SIM.** Уведомления о новых
  пакетах использовали id `2000 + (hashCode and 0x0FFF)`, то есть диапазон `2000..6095`, а
  подтверждение подмены SIM — `4101`: попадание внутрь диапазона означало, что второе уведомление
  затирает первое (ровно тот же класс ошибки, что раньше с `1001` у VPN и блокировщика звонков).
  Все id собраны в `NotificationIds`, уведомления о пакетах переехали в `20000..24095`, а тест
  `NotificationIdsTest` проверяет уникальность одиночных id и отсутствие пересечения с диапазоном
  (6 тестов, включая отрицательный `hashCode`).
- **Решение по входящему SMS вынесено в `SmsSpamDecision`.** Цепочка «белый список → чёрный
  список/спам-база → эвристика ссылки» жила в Android-приёмнике с Room и `PhishingUrlChecker`, и
  ни один тест её не проверял — при этом именно от неё зависит, будет ли сообщение **отменено**.
  Теперь порядок закреплён 7 тестами: белый список сильнее всего, отмена доставки возможна только
  при вердикте `BLOCK_NUMBER`, подозрительная ссылка без блокировки номера даёт предупреждение.
  Эвристика ссылки больше не считается, если номер уже заблокирован (лишний разбор текста).
- **Ещё два интервала переведены на монотонные часы.** Бюджет времени проверки подписей
  (`ApkSignatureCheck`) и окна детектора подглядывания (`ShoulderSurferService`: адаптивный
  интервал кадров и не чаще одного уведомления в 30 с) считались по `System.currentTimeMillis()`
  и «съезжали» при смене времени; на длительности проверки это влияло напрямую.
- **Тест-класс, объявленный вторым в файле, не исполнялся.** `tools/jvm_unit_test.py` брал из
  файла только **первый** класс (`kotlin_class_of`), поэтому второй компилировался и молча
  пропускался — «тесты зелёные», а часть их не запускалась. Теперь собираются все классы, в теле
  которых есть `@Test`, а `--self-test` проверяет это на синтетическом файле с двумя классами:
  с прежним поведением он падает с «ожидалось 3 успешных, получено 1». Дефект нашёлся при
  добавлении второго класса в новый файл тестов приманок.
- **Одно SMS из повторяющихся «a.» роняло проверку ссылок `StackOverflowError`.** В регулярке
  распознавания «голых» доменов был вложенный квантификатор `(?:\.[\w-]+)*\.`: на тексте вида
  `a.a.a.a…` бэктрекинг уходил в рекурсию и падал уже на ~4000 символах. `StackOverflowError` — это
  `Error`, а не `Exception`, поэтому `try/catch` в `PhishingUrlChecker.checkRecentMessages` его не
  ловил: полный скан обрывался, хотя пришло всего одно сообщение. Разбор переписан на линейный —
  текст делится на слова, явные ссылки ищутся простой регуляркой без вложенных квантификаторов, а
  голый домен проверяется по меткам/TLD в обычном коде. Регресс и фаззинг-инварианты закреплены
  в `HostExtractorFuzzTest` (включая мегабайт разделителей и порог по времени).
- **Ссылка со схемой в верхнем регистре не проверялась по базам репутации.** `ThreatIntelClient`
  разбирал хост через OkHttp, но перед этим сравнивал `startsWith("http://")` **с учётом регистра**:
  `HTTPS://Evil.Example/Track` склеивался в `http://HTTPS://…`, парсер отдавал `null`, домен не
  попадал в `hostsToCheck` — то есть такая ссылка проходила мимо URLhaus/OpenPhish молча.
  Разбор вынесен в чистый `HostExtractor` без OkHttp: схема отбрасывается без учёта регистра,
  снимаются `user:pass@`, порт, путь/query/fragment, крайние точки и `www.` (иначе `www.evil.com`
  из SMS не совпал бы с записью `evil.com` в фиде), IPv6/односложные имена/`example.*` отсекаются.
  11 выполняемых тестов.
- **Фишинговая ссылка без схемы не находилась.** В SMS мошенники пишут «Ваша карта заблокирована,
  подробности: `sberbank-online.ru`» — без `http://` и без `/` в конце. `PhishingUrlChecker`
  считал ссылкой только `http(s)://`, `www.`, сокращатели и токены с косой чертой (`.ru/`, `.com/`),
  поэтому такое сообщение не попадало в находки вовсе, хотя ключевое слово в нём есть. Теперь
  дополнительно распознаётся голый домен в частых «фишинговых» зонах (`ru`, `com`, `net`, `org`,
  `info`, `xyz`, `top`, `click`, `site`, `online`, `shop`, `de`, `su`, `io`). Регресс покрыт тестами,
  включая проверку, что «т.е.» и «10.50 EUR» ссылками не считаются.
- **Эвристика фишинга вынесена в `PhishingHeuristics` и реально исполняется тестами.**
  Логика жила в классе с `Context` и OkHttp-репозиторием, поэтому её тест (`PhishingUrlCheckerTest`)
  требует MockK и в JVM-прогон не попадал — то есть проверка фишинга не исполнялась ни разу.
  Чистый объект без Android-зависимостей даёт 9 выполняемых тестов; `PhishingUrlChecker`
  делегирует в него, публичное поведение не изменилось.
- **Заглушка `Context` в прогоне была не абстрактной, хотя в `android.jar` класс абстрактный.**
  Из-за этого в тест попал `Context()` и JVM-прогон его «съел», а настоящая компиляция
  (`kotlin_frontend_check.py` с `android.jar`) упала на
  `Cannot create an instance of an abstract class`. Заглушка приведена к SDK, тест убран —
  проверять `collectEnvironmentSignals` без Robolectric нельзя, о чём и написано в DEVELOPMENT.
- **Проверка оверлеев не находила приложения с разделителями в имени.** `OverlayAttackCheck`
  сравнивал имя пакета и ярлык с шаблонами подстрокой, а шаблоны записаны через точку и дефис
  (`chat.head`, `pop-up`, `screen.filter`, `screen.dim`). В результате `com.x.chathead` с ярлыком
  `ChatHead` — то есть самая частая форма имени — считался безопасным, и чек молчал о приложении
  с правом рисовать поверх других окон. Теперь сравнение идёт по нормализованной строке
  (нижний регистр, без `.`, `-`, `_` и пробелов), поэтому `ChatHead`, `chat_head` и `chat head`
  совпадают, а `Bank`, `Fridays`, `Wikipedia` — по-прежнему нет. Дефект нашёлся сразу, как только
  `OverlayAttackCheckTest` перестал пропускаться в JVM-прогоне.

### Security
- **Подбор PIN по SMS больше не бесконечен.** `SmsCommandReceiver` (`#PG:PIN:CMD`) проверял PIN
  без всяких ограничений — 4-значный код перебирался за минуты. Добавлен
  `util/PinAttemptLimiter` (5 неудач → блокировка 15 минут, успешный ввод сбрасывает счётчик,
  состояние в DataStore — перезагрузка телефона блокировку не снимает; логика покрыта
  `PinAttemptLimiterTest`). При отклонённой команде владелец получает локальное уведомление
  «Попытка управлять телефоном по SMS» (наружу ничего не уходит).
- `setPin()` отклоняет нецифровой/короткий PIN: раньше его можно было сохранить, и тогда
  SMS-команды (`\d+` в шаблоне) переставали совпадать с PIN — удалённое управление ломалось молча.
- **Перенос данных на новое устройство закрыт.** `android:allowBackup="false"` сам по себе не
  запрещает Device-to-Device transfer на Android 12+: правила нужно задавать в
  `dataExtractionRules`. Файл `res/xml/data_extraction_rules.xml` существовал, но не был подключён
  к манифесту и **включал** `sharedpref` (хэш PIN, ключи) в копию. Теперь он подключён и исключает
  все домены (`root`, `file` — сейф и фото вторжений, `database`, `sharedpref`, `external`)
  и для cloud backup, и для D2D; `backup_rules.xml` приведён к тому же виду как fail-safe.
- **`<uses-feature required="false">`** для камеры, вспышки, микрофона, GPS и телефонии: без них
  Play считал эти модули обязательными и скрывал приложение от Wi-Fi-only планшетов.

  друг друга, NPE при отзыве доступа, лимит размера не проверялся.
- `DatabaseKeyManager`: `apply()` мог потерять пароль БД, отсутствие ключа давало невнятный каст-эксепшен.
- `PdfExportHelper`: после разрыва страницы текст рисовался на canvas предыдущей страницы.
- `PermissionAbuseCheck`: проверялись запрошенные, а не выданные разрешения.
- `SystemIntegrityCheck`: рефлексия `SystemProperties` на Android 9+ не работает, `/system/bin/debuggerd`
  есть на всех устройствах (ложные срабатывания).
- `RootDetectionCheck`: лишний `File`, `Runtime.exec` без `waitFor`.
- `SpywareCheckRepository`: подпись APK не анализировалась; UID-кэш фаервола терял пакеты с общим UID.
- Onboarding/consent: побочный эффект вызывался в теле композиции.
- Vault: `InputStream.available()` вместо реального размера, отсутствие `USE_BIOMETRIC` в манифесте.
- Язык интерфейса: селектор не применялся и сбрасывался при перезапуске; теперь язык хранится в
  SharedPreferences-зеркале и применяется в `MainActivity.attachBaseContext()`, выбор пересоздаёт Activity.
- Экран согласий: галочки были декоративными — системный запрос разрешений не вызывался
  (SMS, геолокация, уведомления, камера не работали). Теперь галочка запускает
  `RequestPermission`, состояние берётся из реального гранта, при отказе доступна ссылка в настройки.
- Уведомления и SMS (`ShoulderSurferService`, `IntrusionResponseService`, `IntrusionResponse`,
  `SimSwapDetector`) берут текст из ресурсов, а не из русских литералов.
- Ошибки хранилища и экспорта логов: вместо русских строк — типизированные коды, текст в UI;
  Toast об экспорте больше не повторяется на каждой рекомпозиции.
- «Удалённое стирание/блокировка» больше не ссылаются на удалённый FCM — подсказывают SMS-команды.
- `CallBlockerScreen`: ошибка «некорректный номер» теперь видна (snackbar), раньше молча игнорировалась.
- Периодическое сканирование ставилось в очередь при каждом старте приложения даже при выключенной
  настройке — теперь работа создаётся/отменяется по `isScheduledScanEnabled`, а код расписания
  живёт в одном месте (`ScheduledFullScanWorker.schedule/cancel`), а не в трёх копиях.
- Текст этапов полного сканирования был зашит по-русски в оркестраторе — теперь `ScanStage`
  с `@StringRes` и подстановкой на экране (ru/en/de).
- Чек телефона перечисляет установленные приложения один раз вместо трёх (`getInstalledApplications`
  вызывался трижды за проверку).
- Полнота локалей en/ru/de (все ключи синхронизированы), темы `values-night`, `QUERY_ALL_PACKAGES`,
  keep-правила R8 для apk-parser/libphonenumber/OkHttp.

### Removed
- `util/SslPinningUtil.kt` — неиспользуемый «задел» под пиннинг: ни одного вызова, ни одного пина;
  оставлять файл с таким именем значит создавать иллюзию защиты. Threat-intel ходит по HTTPS через
  OkHttp с системным хранилищем сертификатов.
- `model/SmishingSms.kt` — неиспользуемые entities `smishing_sms`/`known_phishing_domains` и enum
  `SmishingStrictness`: они не входили в `@Database`, на них никто не ссылался, а `List<String>`
  в них не имел `TypeConverter` — при регистрации таблицы сборка бы упала.
- `intrusion/IntrusionResponseService.kt` — мёртвый foreground-сервис (см. Fixed).

### Changed
- **Удалён Firebase** (Analytics, Crashlytics, Performance, BOM, плагин, `google-services.json`):
  проект заявляет «Zero telemetry», а `logCallBlocked` отправлял номера телефонов.
- Удалены неиспользуемые `SimChangeReceiver`, `model/SwapEvent.kt`, `ui/navigation/DrawerContent.kt`.
- README/PRIVACY_POLICY/RELEASE приведены в соответствие с фактическими интеграциями.
